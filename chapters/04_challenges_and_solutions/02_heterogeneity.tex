\subsection{Hardware Heterogeneity}

\subsubsection{Challenge 2.1: Architecture Search on Heterogeneous Hardware}

Clients participating in NAS-in-FL can vary widely in computation and memory capacity. One client may be able to evaluate a candidate architecture within seconds while another would take minutes to evaluate it. As a result, slow devices delay the architecture search. Some clients may also struggle to fit certain candidate architectures into their memory, so practitioners must adjust the NAS-in-FL to account for this.

\subsubsection{Solution 2.1a: Matching Local Search Work to Client Capacity}

Resource-aware methods restrict each client to a feasible supernet subsubspace, subnet, number of cells, or local optimisation budget, so its search work follows its computation and memory capacity \cite{fedoras_2022,apons_2023,divide-and-conquer_fednas_2023,peaches_2024,fgfl_2024,supernet_trade-off_fednas_2025}.

\subsubsection{Solution 2.1b: Grouping Clients by Training Latency}

NASFLY profiles client computation and communication costs and forms split-learning groups that minimise mean waiting latency during supernet training \cite{nasfly_2024}.

\subsubsection{Solution 2.1c: Tolerating Slow or Stale Clients}

Straggler-tolerant search removes hard round barriers or down-weights stale client updates, preventing slow clients from blocking or unduly biasing the search \cite{rl_fednas_2021,fedregnas_2025}.

\subsubsection{Solution 2.1d: Accounting for Unequal Supernet Exposure}

Exposure-aware aggregation averages each supernet parameter only across the clients that trained it, accounting for the unequal operator or width coverage produced by hardware-feasible subsubnets \cite{fedoras_2022,fgfl_2024,supernet_trade-off_fednas_2025}.

\subsubsection{Solution 2.1e: Keeping the Full Search Model on the Server}

Server-side methods keep the search space or full supernet off clients: clients receive one sampled candidate, query a cloud supernet for a feasible subnet, or train a lightweight knowledge model from which the server trains the supernet \cite{perfedrlnas_2024,rafl_2024,hapfnas_2025}.

\subsubsection{Challenge 2.2: Searching architectures deployable to heterogenous clients}

In NAS-in-FL, the searched architectures are usually trained as well as deployed on the same set of devices. This means in addition to taking client heterogeneity into account at search time, the NAS-in-FL method needs to account for the heterogeneous deployment environment as well. A single architecture tailored to the least capable device can leave the resources of more capable devices unused, while an architecture tailored to the most capable device hardware may be infeasible for deployment on less capable clients \cite{fedoras_2022}. In a cross-device setting, the variance between client hardware capabilities is particularly pronounced.

\subsubsection{Solution 2.2a: Per-Client Personalisation}

\subsubsection{Solution 2.2a: Searching Separate Architectures for Hardware Tiers}

Tier-based search assigns clients with similar inference budgets to a common hardware tier and searches one feasible architecture for each tier \cite{fedoras_2022,clustered_direct_fednas_2022,fgfl_2024}. This lets stronger devices use more of their capacity than a model sized for the least capable tier.

\subsubsection{Solution 2.2c: Training a Shared Supernet for Constraint-Specific Local Selection}

After training a weight-sharing supernet, clients select subsubnets or exits that fit their compute and memory limits and rank well on local validation data \cite{superfednas_2024,hapfnas_2025,enasfl_2024}. This permits architectures to reflect per-client hardware and data heterogeneity while retaining a shared weight space.

\subsubsection{Solution 2.2d: Including Hardware Costs in the Search Objective}

Hardware-aware search adds a hardware cost, such as measured latency or a MAC budget, to the accuracy objective and selects a candidate within the target limit \cite{clustered_direct_fednas_2022,load_monitoring_fednas_2025,fgfl_2024}. Using a different budget or latency profile for each device or hardware group yields architectures tailored to different inference hardware.

\subsection{Client Data Heterogeneity}

\subsubsection{Challenge 2.3: Differing Client Data Distributions}

Client data can differ in class balance and feature distribution, for example because mobile-phone users have different usage patterns. As clients evaluate candidate architectures on their local data, they may favour different operations or rank the same candidates differently \cite{collaborative_nas_for_pfl_2025,superfednas_2024}. These conflicting evaluations and training updates make the global search signal inconsistent and can make inherited-weight candidate rankings unreliable \cite{hapfnas_2025}.

\subsubsection{Challenge 2.4: Imablance Client Data Volumes}

Some clients can hold significantly more training data than others. Consequently, estimates of candidate performance from small local datasets can be noisier than those from large datasets. Unequal sample counts can also give data-rich clients more influence over shared weights and architecture decisions, causing the search to favour their data characteristics \cite{fednas_2021}.

\subsection{Client Networking Capability Heterogeneity}

\subsubsection{Challenge 2.5: Bias from Overrepresenting Frequently Available and Well-Connected Participants}

Network conditions and availability cause some clients to participate more often than others. Clients with slow or unreliable links, low battery, or long candidate runtimes miss more round deadlines, so their data affect fewer architecture decisions \cite{optimize_fednas_edge_2021,peaches_2024}. Resource-aware schedulers can compound this imbalance by assigning poorly connected or low-capability clients only small candidates \cite{fedoras_2022}. Each candidate is then trained on a different, non-IID client subset, which couples its apparent quality to the data it received. In weight-sharing searches, this coupling produces conflicting shared-weight updates and unreliable candidate rankings, biasing the search towards frequently available and well-connected clients \cite{hapfnas_2025}.

\subsubsection{Solution 2.5a: Balancing Connectivity and Data Coverage Jointly}

Candidate-training groups can be formed using both network constraints and data coverage, preventing connectivity alone from determining which data train each architecture. Group membership is adjusted to give each candidate a more representative data mixture while keeping its communication or completion time feasible. For example, NAFNAS groups clients by bandwidth and class distribution, while FINCH minimises each cluster's distance from the population distribution under a completion-time limit \cite{network_aware_fed_nas_2025,finch_2024}. These joint assignments make candidate evaluations more comparable because network conditions have less influence on the data seen by each architecture.

\subsubsection{Solution 2.5b: Decoupling Client Knowledge from Candidate Assignment}

Client knowledge can be aggregated into a common teaching signal before it is used to train different candidate architectures. Each candidate then learns from several clients, rather than only from the devices capable of executing it. For example, HAPFNAS distils averaged predictions from lightweight client models into sampled supernet paths, while PAS uses ensembled client feature maps to guide heterogeneous personalised architectures \cite{hapfnas_2025,collaborative_nas_for_pfl_2025}. Knowledge aggregation therefore transfers information across architecture boundaries without requiring every client to train every candidate.
